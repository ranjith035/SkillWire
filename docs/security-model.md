# ASP Security Model & Threat Analysis

This document outlines the security architecture, threat model, and mitigation strategies for the AI Skill Protocol (ASP).

---

## 1. Threat Model

Because AI skills consist of executable instructions ingested directly into Large Language Model system prompts, they introduce unique attack vectors that combine classical software supply chain risks with AI-specific prompt injection vulnerabilities.

### 1.1 Threat Vectors

| Threat ID | Threat Category | Description | Impact |
|---|---|---|---|
| **T-01** | **Package Tampering** | An attacker intercepts or alters a `.skill` package in transit or in a compromised mirror. | Malicious instructions delivered to client runtime. |
| **T-02** | **Indirect Prompt Injection** | Instructions in a dependency contain hidden directives to exfiltrate context or bypass system guardrails. | Data exfiltration, jailbreaks, elevation of privilege. |
| **T-03** | **Excessive Permission Escalation** | A skill requests execution access or filesystem access disproportionate to its described purpose. | Arbitrary command execution on host developer machine. |
| **T-04** | **Dependency Confusion / Typosquatting** | Attacker registers a malicious skill with a similar name or ID in an unauthenticated registry. | Downstream developers unknowingly install malicious skill logic. |
| **T-05** | **Path Traversal in Archive** | A malicious `.skill` tarball contains entries with `../` attempting to overwrite arbitrary host files during unpacking. | Host system compromise. |

---

## 2. Defensive Controls in ASP

### 2.1 Cryptographic Integrity Verification (Mitigates T-01)
* Every `.skill` bundle generated by `asp pack` calculates a SHA-256 digest of `skill.yaml` and records it in `skill.lock`.
* During `asp install` or `asp unpack`, the lockfile is verified against the extracted contents. If any discrepancy is detected, the operation immediately aborts with an `IntegrityError`.

### 2.2 Explicit Permission Boundaries (Mitigates T-03)
Skills must declare runtime capabilities inside their manifest:
```yaml
permissions:
  network: false
  filesystem: false
  code_execution: false
  tool_use: false
```
* By default, all permissions are `false` (sandboxed).
* The CLI prompts for user approval before installing any skill requesting elevated permissions unless explicitly overridden with `--yes`.
* Host runtimes (Claude, Gemini) can inspect these flags and restrict tool execution accordingly.

### 2.3 Safe Archive Extraction (Mitigates T-05)
The unpacker (`asp.core.packager.unpack_skill`) enforces strict validation on tarball members:
* Relative path traversal patterns (`..`) are strictly rejected.
* Absolute file paths in member names trigger immediate extraction rejection.
* Unpacking occurs in isolated, ephemeral temporary directories before final relocation.

### 2.4 Reverse-Domain Identification (Mitigates T-04)
Skill IDs follow reverse-domain notation:
```
io.github.username.skill-name
org.enterprise.security-review
```
This binds namespace ownership to verified domain or source-control identities.

---

## 3. Best Practices for Skill Consumers & Enterprise Deployments

1. **Commit `skill.lock`**: Always commit the generated lockfile to version control to guarantee deterministic, tamper-proof builds.
2. **Review Skill Instructions**: Use `asp validate` or inspect the manifest before running skills in production.
3. **Run Least Privilege**: If a skill does not declare `code_execution: true`, never expose terminal or bash tools in its execution context.
